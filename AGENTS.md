## Verifying anything behind a login

`/insights`, `/profile` and `/settings` `router.replace("/")` for anonymous visitors; `/library` and `/wishlist` render a sign-in gate instead (2026-08-18) and the item-detail personal block swaps to its anon controls. Either way **the real content can't be checked without a session.** Use **`GET /api/dev/login`** — it mints one for the `users.id` in `DEV_LOGIN_USER_ID` and redirects to `/`; the local `.env` already points at the real account. Works in the in-app browser pane.

Don't hand-mint a JWT (the harness blocks it as credential-forging, correctly) and don't assume anon-only verification is the best available — that assumption is why several batches shipped "not yet verified logged-in". **Never call `/api/auth/logout` to test the anon side**: it bumps `session_epoch` and kills Nils's own browser session, which only a real OAuth round-trip restores.

The route's three fail-closed gates (`NODE_ENV !== "production"` · loopback host · a real identity row) are what keep it off fandex.org. Do not relax them, and treat it as auth code — main-loop only, per the routing rules below.

## Load-bearing invariants (don't relearn these the hard way)

- **The prune invariant:** a sync pull that fails must THROW, never return `[]`/partial. `syncProvider` (`src/lib/sync/index.ts`) deletes every local entry missing from a successful pull, so a swallowed error silently wipes the user's library. When adding any adapter: a pull that can't complete must throw; a pull that legitimately found nothing may return `[]`. **Anything a pull carries beyond ids inherits this** — MB14's per-episode state rides on Trakt's existing library pull precisely so it can't diverge, and its reconcile sits INSIDE `syncProvider`'s try, after the pull, so an outage is a no-op instead of a wiped watch history. Corollary for any optional per-item payload: **`undefined` and `[]` must mean different things** — "this pull says nothing about X" vs "this pull is authoritative about X and there is none". Conflating them is how an empty pull deletes data. A declared capability (`capabilities.episodes.read`) is the gate, never a sniff of the returned shape.
- **A component that renders `null` when empty must know WHY it is empty before it ships.** Twice in one day (MB14's Home rail and its item-page twin): each returned `null` for four unrelated states — no data yet, the provider pull is FAILING, still filling a cache, genuinely caught up — so a real, diagnosable problem read as "the feature doesn't work" with nothing to go on, and the person looking at it was on a phone with no console. `return null` on an empty state is not a neutral default; it is a decision to discard the only evidence anyone will get. The fix both times was the same: a `*Status`/`*Diagnostic` function returning the counts that separate the cases (computed independently, so a throw in the main path can't take the explanation down with it), a provider write logging the SHAPE of what it pulled and not just what it stored, and one line of copy that never claims success it cannot see.
- **When ONE component is fed by TWO routes, every field the shared code reads must arrive from BOTH — and the half that is missing fails silently, as an inert control rather than an error.** (2026-08-26.) `/library` and `/wishlist` are one component (`MyStuffView`) over `/api/library` and `/api/calendar`. `/api/calendar` selected `uw.added_at`, put it on an intermediate object, then assembled its response field by field and never copied it across, so every wishlist item reached the client with `addedAt: undefined`. `sortItems` maps a missing timestamp to `-Infinity` (correct — a null must never look like "just added"), the whole list tied, `Array.sort` is stable, and the wishlist kept the route's own release-date order. **The DEFAULT sort did nothing from the day it shipped** (H1.6f, 2026-07-27) until a title added a minute earlier failed to appear at the top a month later. Nothing catches it: `EnrichedItem.addedAt` is optional by design (a Discover card genuinely has no added-at), so `tsc` is happy, lint is happy, 1,049 tests were green, and the response is a valid, fully populated item in every other respect. `src/lib/listRouteSortFields.test.ts` now diffs the two routes against the fields the sort reads. ⚠️ **Corollary — `addedAt` is the one field a merge cannot resolve by keeping the richer copy.** Every other field describes the ITEM; this one describes an EVENT, and an item in both collections has two (wishlisted in June, bought in July). `mergeMyStuff` keeps the library copy, so the wishlist tab was sorting by the purchase; the wishlist's own timestamp is now carried alongside as `wishlistAddedAt` and the tab picks via `asWishlistAdds`. ⚠️ **`smoketest.md` step 13b checked the sort on Library ONLY**, which is exactly why a month passed — when a check names one of two surfaces that share a component, it is testing the component's luck. → [[shared-view-two-routes]]
- **A new table referencing `media_items` must be added to `dbPrune.ts`'s `PRUNABLE_WHERE`.** The boot prune is **default ON in prod** and deletes `browsed = 1` catalog rows nobody "acted on" — where acted-on is a hard-coded list of the tables that cascade off `media_items`. MB14's `user_episode_state` was the fourth: ticking episodes writes none of the other three, so a show tracked but never rated or saved stays `browsed = 1`, and without the clause the next deploy would have cascaded that watch history away. The predicate's own comment already says why it names tables rather than trusting one to be a superset — extend the list, don't reason about whether it's implied.
- **SQL that reaches the SCHEMA must parse on the SQLite LITESTREAM embeds, not the one `better-sqlite3` ships — and the failure is total, silent, and only visible in the backup daemon's log.** Migration 16 put `json_group_array(source ORDER BY source)` in the `user_watchlist` view on 2026-08-17. `ORDER BY` inside an aggregate's argument list is **SQLite 3.44.0+** (2023-11-01); better-sqlite3 ships 3.53, **Litestream v0.3.13 embeds ~3.40**. SQLite parses the ENTIRE schema before preparing ANY statement, so Litestream could not run one query: it logged `malformed database schema (user_watchlist) - near "ORDER": syntax error` once a second and **replicated nothing for two days**, while Railway volume backups are Pro-plan only, so that was the only copy of the database. Everything else stayed green — 820 tests, lint, `next build`, `/api/health` reporting `db: up`, every read site working — because the only process that could not read the schema was the one whose output nobody watches. **It also produced a symptom that was written off as a quirk:** the 340 MB WAL that "cannot be reclaimed while Litestream runs" was this bug (Litestream could not advance its read position, so SQLite could not checkpoint past it, so `wal_checkpoint(TRUNCATE)` answered `busy: 1`). Rules: **express sorting as `ORDER BY` in a SUBQUERY, never inside an aggregate's arguments** (SQLite deliberately won't flatten an ORDER BY subquery into an outer aggregate query, so the order is preserved byte-for-byte — verified on 2,023 live rows); **check any new schema SQL with an OLD `sqlite3` CLI against a copy of the DB**, which is a 10-second test and the only one that catches this; **a restore drill proves the backup you had that day, not the one you have now — re-run it after any schema change**; and **a WAL that will not truncate is a symptom to chase, not a high-water mark to document.** → [[prod-incidents]]
- **An AGE cap is not a SIZE cap, and a boot-only sweep is not a schedule.** `facet_page_cache` shipped 2026-08-13 with a 24 h TTL swept once per boot at 2000 rows, and by 2026-08-19 held **24,953 rows / 222.8 MB — 80.2% of a 331 MB database** that had measured 37.7 MB the day before it landed. Two independent holes. (1) Prod runs for **days**, so a boot-only sweep never ran; anything expiring in-process expired only in theory. (2) The writer is somebody else's **crawler** walking the person/tag/studio long tail, so inside one TTL window every row is "fresh" by definition and the age sweep had nothing to collect while the table grew all day. Nothing catches this: tests, `tsc`, lint and the build are all green, `/api/health` reports the file size but not what is in it, and it surfaces as **container memory** (cgroup v2 bills page cache, and page cache tracks FILE SIZE) rather than as a database problem. Rules that came out of it: **any table written on a request path needs a row or byte ceiling, not just a TTL**; **run the bound on an interval, unref'd, in bounded batches** (better-sqlite3 is synchronous and Litestream holds a second connection); **evict by write time, not read time** — tracking reads turns every cache HIT into a write, which is the shape that caused this; and **deleting rows does not shrink the file** — the pages go on the freelist. **You almost never need to do anything about that:** `db.ts` runs a `VACUUM` after any migration actually applies, which took prod 331.4 → 154.2 MB unprompted, **with Litestream attached and no lock trouble**. The manual lever, when no migration is pending, is `POST /api/dev/prune {"action":"vacuum","confirm":"VACUUM"}`, which checks `volumeInfo().hasRoomToVacuum` first. Do not add a third mechanism; one was added and removed the same day. → [[prod-incidents]]
- **A provider's response SHAPE is not verifiable from its documentation, and a mocked test of an assumed shape proves nothing.** Trakt documents `/sync/watched/shows` as returning `seasons` by default (only `?extended=noseasons` suppresses it). It **does not** — `seasons` is **absent**, not empty, on all 280 entries, with `?extended=full`, plain+paginated, and plain+unpaginated (which also silently returned **100 of 280**, so it is paginated too). MB14 shipped reading episodes off that response and attached **zero** for four deploys; a run-time fallback grafting seasons from the plain call hit a second empty well; and the unit test asserting the graft worked **passed**, because it mocked the shape the docs implied. `tsc`, `npm run lint`, **750 tests** and `next build` were green throughout. The fifth deploy added a shape probe (`/api/dev/trakt-shape`) instead of another inference and answered it in one call. **When a provider integration returns nothing, probe the payload before theorising about the code** — and prefer a check the environment can actually run (a call count) over asserting a payload you had to invent. Episodes come from **`/sync/history/episodes`** (bulk, one entry per play → dedupe) or **`/shows/{id}/progress/watched`** (per-show; ⚠️ lists every aired episode, so only `completed: true` counts). → [[trakt-episode-endpoints]]
- **Per-source FAILURE isolation is not per-source LATENCY isolation, and the breaker must THROW.** Every provider adapter try/catches, so one dead source never *broke* a page — but the caller still *waited* for it. RAWG going down (Cloudflare 522, ~19.8 s) × `http.ts`'s two 5xx retries = ~60 s per call; `fetchPages` fires 5 pages under one `Promise.all` and `/api/home` reaches RAWG twice, so a cold `/api/home` measured **2.2 minutes** (2026-08-02). `http.ts` now has a per-host circuit breaker + an optional `budgetMs`; browse paths pass `BROWSE_BUDGET_MS`, **sync/pull deliberately keeps its unbounded budget**. **The breaker throws `ProviderUnavailableError` and must never fabricate a Response** — a synthetic 503 would need zero call-site changes and would ALSO be read as `!res.ok` by the pull adapters, turning an outage into an empty library under the prune invariant above. Browse code opts into degradation explicitly (`bestEffort` in `discoverFeed.ts`); pull code keeps throwing. Also: **measure before optimising** — the 58 s cold Discover load was blamed on the catalog pool cache for days; the pool rebuild is ~430 ms (`scripts/probe-pool.mjs`), and the 58 s was entirely this.
- **If a medium has two providers, a single-source pull is a bug — and the surfaces disagree by default.** ⚠️ **Scope changed 2026-08-23 (PL3) and the split is now the point: this holds for the BROWSE feed, where RAWG is still pulled alongside IGDB, and NOT for the facet paths, where RAWG was removed entirely.** Cutting RAWG from browse was tried and reverted the same day because `discoverFeedSources.test.ts` failed: Steam has no date-windowed pagination, so browse would have gone IGDB-only, and browse measures **0** RAWG calls against the facet path's 4. Do not "finish the job" without reading that test. Games are served by RAWG *and* IGDB. `personalizedFeed` pulled both; three other paths pulled RAWG alone, and nobody noticed until RAWG actually went down (2026-08-02) and those three lost the entire media type while the feed beside them carried on: the games **load-more** returned `[]` forever with the button still enabled (a silent dead control), `/api/discover`'s **cold-start/anonymous** branch left logged-out visitors with no games at all while signed-in ones were fine, and `/api/home`'s trending rail dropped every game so the whole "Popular right now" section vanished under the Games filter. The dual-source pull now exists ONCE (`fetchGamePageAllSources` / `fetchTrendingGames` / `dedupeGames` in `discoverFeed.ts`) — one correct copy plus three single-source ones is exactly how they drifted. When touching any games surface, check **all** of them: initial browse, load-more (a *different* code path from the browse), trending, calendar-popular, profile. And test the invariant that matters — *a games pull survives one source being down* — not the happy path, which passed throughout the outage.
- **A public item url is `/{type}/{slug}` and the slug is IMMUTABLE, stored, and unique per type.** (2026-08-21.) The url used to be `/{type}/{uuid}/{cosmetic-slug}` and the uuid is a ROW id: the boot prune deletes browsed-only rows on every deploy, so re-opening such a title minted a new row, a new uuid and a new url, leaving the old one a hard 404 — two dead urls for one film in an afternoon. A title-derived slug survives a delete-and-recreate because it names the WORK, not our storage. Three rules follow. **`media_items.slug` is assigned once, by `ensureItemSlug` in matcher.ts's create path (AFTER `remergeItem`, so it uses the merged title), and never changed** — a url that moves when a provider retitles a film is a url nobody can share. **The legacy 3-segment route must stay** (`[type]/[slug]/[legacy]`): it 308s, and every link ever shared points at it. **Collisions are real and stored-ness is what handles them** — 40 of 2,530 titles collide within a type (Dracula, Nosferatu, Godzilla, The Lion King), first-come keeps the bare slug and the newcomer takes `-{year}`; computing the slug at read time would send both Draculas to one page. When adding a payload that feeds a card, thread `slug` through it: `publicItemHref` falls back to the legacy uuid url, which works but costs a 308 on every click. → `src/lib/publicUrl.ts`, `src/lib/itemSlug.ts`
- **A selection must rank by the same quantity the thing it feeds is made of, and a row must name the input it was actually computed from.** (2026-08-22, both in `computeFandexScore`.) The Score's five top-N buckets sorted by the raw `dev` while a facet's contribution, and the number the panel prints, is `dev · classWeight · gain` — identical only when every class weight is 1, which they never are (`roleWeights` ships director 1.3 against cast 0.6; prod runs `ip` 3 / `director` 2; tag category weights are an admin knob). So a heavier facet worth MORE points lost its slot to a lighter one with a bigger raw deviation, and the panel showed a greyed "not counted" row worth **twice** the counted row above it. It bit people and companies hardest, because their weights differ *by design*: the role weights exist to say a director outranks a cameo, and only the SCORE ever read them. Same function, second instance of the same shape: `reasons[].category` carried the ITEM's facet category while the weight came from the profile's EFFECTIVE category (post `tag_category_override`), so "Role-playing (RPG)" printed as OTHER while scoring as genre — and `facetColorVar` reads that field, so the colour was wrong too. Corollary that fell out of fixing it: **`CATEGORY_LABELS` in `tags.ts` is nine STATIC ids and the taxonomy is editable** — the live DB already holds `modes`, `objects-elements`, `people-characters`, so resolve a category label against the live list (threaded down as a prop, viewer-independent) and fall back to the id, never to a flat "Tag". Note the fix pulls cast `prominence` into the selection too, and **moves scores** wherever a weight is not 1. ⚠️ **`docs/fandex-score.md` §3.3 specified `sorted by |dev·W|` from the day the top-N shipped (2026-07-29) and the code never matched it** — a spec this specific is worth diffing against the implementation, because nothing else will. → [[fandex-score-h5]]
- **A single-provider sync must not refresh the staleness clock for every provider.** (2026-08-22.) `MyStuffView` decided whether to auto-sync by collapsing the whole log with `Math.max(...syncLogs.map(l => l.last_sync))` and firing `syncToCompletion("all")` only if that ONE timestamp was over 24 h old. On 2026-08-16 the Home progress rail shipped `syncToCompletion("trakt")`, and from that day every Trakt-only run made Steam, RAWG and TMDB look fresh: **Steam last synced 2026-08-02 and nobody noticed for three weeks**, surfacing as a game staying on the wishlist weeks after it was bought (Steam had already dropped it; nothing was asking Steam). The per-provider breakdown was in the payload the whole time — `/api/auth/me` returns `MAX(synced_at) … GROUP BY provider` — and only the client threw it away. `staleProviders()` in `syncClient.ts` is now the one decider (per connected identity, prefix-matching a provider's suffixed `steam-library`/`trakt-episodes` rows), and `syncToCompletion()` takes a provider LIST. ⚠️ **An empty list must be an explicit no-op**: `/api/sync`'s `providerQueue` falls back to the whole registry on an empty `providers`, so passing one through turns "nothing is due" into a full sync on every visit.
- **A provider call that carries only an APP credential must opt into the 401/403 latch with `appScopedAuth: true`, and forgetting it fails SILENTLY.** (2026-08-22.) `http.ts` deliberately never opens the breaker on a 4xx, so our own bad request cannot take a healthy host down for everyone. That is right for a one-off and wrong for a persistent one: prod sent **13,068** requests to RAWG, 4,343 to OMDb and 3,155 to Letterboxd in 10.5 h and **every single one returned 401** — about a third of all provider traffic, re-asked forever with nothing learning from it. Five consecutive 401/403s now open the host for 15 min, doubling to a 6 h ceiling, and any other response clears the run so a provider that starts answering is picked straight back up. ⚠️ **Only APP-scoped calls count, and that split is load-bearing**: RAWG and TMDB serve app-key metadata and per-user calls from the SAME host, so counting a user-scoped 401 would let one person's expired token stop the provider for everybody. Opt-in is per CALL SITE, not per host. **The first pass proved how quietly this fails** — it marked `src/lib/sources/` and missed `facetDetail.ts` + `discoverFeed.ts`, which is where a cold facet page's RAWG calls actually come from, so prod took 39 consecutive 401s with the breaker still closed while tsc, lint, 935 tests and the build were green. `src/lib/httpCallSites.test.ts` now fails if any `httpFetch` carries an app key in its query string without the flag (it skips TMDB's `session_id=` and `/authentication/`, which legitimately carry a user credential alongside).
- **A cache goes through `sharedCache(name, opts)`, NEVER `new BoundedCache()`.** (2026-08-23.) Next resolves a module into a different bundle per route kind, so a bare module-scope cache becomes SEVERAL independent caches, one per bundle that imports it — the same trap that silently broke the circuit breaker for three weeks. `sharedCache` pins them to `globalThis` by name, and `/api/health`'s `caches` then reports the TRUE process-wide size. ⚠️ **Two consequences.** The name is the identity, so two different caches sharing a name would silently share STORAGE. And a process-wide cache survives between TESTS: `vitest.setup.ts` clears them all in a global `beforeEach`, which it has to — a provider test started failing the moment they were pinned, because an earlier test had cached that lookup. (That example was omdb's; PL1 deleted the module and its suite on 2026-08-23, but the trap is unchanged and the global `beforeEach` is still why nothing else hit it.) ⚠️ **Bounds are ENTRY COUNTS, not bytes**, and `GET /api/dev/dbsize?caches=1` is what tells you what a `max:` actually authorises: measured 2026-08-23, `facetCache.derived` is 16.8 KB/entry (33 MB now, 98 MB at its cap) while the uncappable discovery pool is only 5.2 MB. → `docs/scalability.md` §6
- **The discovery pool must NOT be capped, and it grows at 2.6 MB per 1,000 catalog items.** `_cache.vectors` in `discovery.ts` is one `DiscoveryVector` per pool item plus a `byId` Map over the same objects. A `BoundedCache` there would not lose a cache entry, it would silently change everyone's Fandex Score, "More like this" ranking and IDF weights, because the pool IS the candidate set. Measure it (`poolWeight()`) and plan for the slope; never truncate it.
- **Identical WARM and COLD timings on a route mean there is no cache at all**, and that is a cheaper diagnosis than reading the code. `/api/discover` answered in 930 ms warm and 955 ms cold until `discoverFeed.ts` got a page cache (2026-08-23); it now answers in ~95 ms and costs **0** TMDB calls per request. Every provider boundary in the app is cached now — if you add one, cache it, pin it to `globalThis`, and **never cache an empty result**, which would pin a provider outage in place for the whole TTL.
- **The thin-write / pool rule:** a discover-time write is insert-only and stamps `browsed=1` / projection version `0` — it must never overwrite or degrade a real synced/ingested row.
- **Migrations have TWO apply paths** — in-process via `getDb()` (what tests/prod use) and standalone via `node scripts/migrate.mjs` (plain Node, resolves neither the `@/*` alias nor extensionless specifiers). Green tests only prove the in-process path. After touching `migrations.ts`, run the standalone script against a DB copy.
- **`db.ts`'s `CREATE TABLE`/`CREATE INDEX` block runs BEFORE migrations** and must stay valid against an OLD (pre-migration) schema. A column added by a migration must have its index created in that *same* migration, never in the schema block — putting them together only works on a fresh DB and silently breaks every upgrade path.
- **Any route reading an env var to build an absolute URL (`BASE_URL`, etc.) must export `dynamic = "force-dynamic"`.** Next prerenders route handlers without it at `next build` time, and Railway's build-phase env can differ from its runtime env (confirmed: `NEXT_PUBLIC_BASE_URL` resolves correctly at runtime but wasn't available at build) — the wrong value gets baked into the static output permanently, invisible until you actually read the response body (status 200 either way). `sitemap.ts` had this from the start; `robots.ts` didn't and shipped `localhost:3000` to prod until a live smoketest caught it (SM7, 2026-07-19). `/legal/[locale]/[doc]` (H4.1, 2026-07-30) is the same trap: `generateMetadata` builds canonical + hreflang URLs from `BASE_URL`, so it needs the export too — verify with `npm run build`'s route table showing `ƒ (Dynamic)`, not `○ (Static)`.

- **Anything a CLIENT component renders must never reach a module that imports `db.ts`, and the failure is a 500 on the page with every check green.** (2026-08-26.) `roleLabel` lived next to the ranking code in `popularPeople.ts`; `PersonCard` imported it; `HomePageClient` is `"use client"`. Turbopack followed `PersonCard -> popularPeople -> db.ts -> better-sqlite3` into the BROWSER bundle and `/` returned `Can't resolve 'fs'`. `npx tsc --noEmit`, `npm run lint` and **1,019 tests** were all clean, because nothing but loading the page exercises the client/server module graph. The fix is a LEAF module with no imports (`src/lib/personRail.ts`) holding the shape and the labels, imported by both halves. ⚠️ **A `import type` is erased and is always safe; a runtime value is not.** ⚠️ And once Turbopack has cached the bad graph, `.next` keeps replaying the error after the fix, so a stale `Module not found` needs `.next` deleted before you believe it.
- **A client island fed by `/api/` is invisible to Google, not "probably seen".** (2026-08-26.) `/api/` is under the robots `Disallow`, and **Googlebot's renderer honours robots.txt for SUBRESOURCES**, so a rail whose data arrives via `useEffect` fetch of `/api/home` could never produce a crawlable link: the renderer was blocked from fetching what would have produced it. `/`'s public rails now come from the daily `home_snapshot` and are handed down as PROPS. Nothing about the components changed: `PosterCard` always rendered a real `<a href>`, and a client component's first render IS server HTML. **Where the data comes from was the only thing that made those links invisible**, so "make it a server component" is usually the wrong prescription and "pass the data in" is the right one. → `docs/seo.md`
- **The daily `home_snapshot` has four rules, and three of them are the shape of an incident already on file.** (2026-08-26, `src/lib/homeSnapshot.ts`.) One provider fan-out per DAY, stored, served to everyone: measured **0 provider calls across 6 page loads** of `/`, where every cold cache entry used to cost TMDB + Trakt + IGDB + RAWG. (1) **A failed build must never replace a good snapshot**. Clearing the table before rebuilding, which is the obvious design, turns a provider outage into an empty homepage; the write is one atomic replace AFTER a build that validated. (2) **The builder writes catalog rows on purpose and PR15 still holds**. It calls `persistDiscoverItems` directly rather than handing `persistDiscoverBatch` a fake user, so the request-path gate keeps its shape; the write is bounded at 30 titles a day regardless of traffic. (3) **`home_snapshot_item` is the FOURTH entry in `PRUNABLE_WHERE` and the first that is not user state**, and the refresh is sequenced AFTER `bootPrune` resolves, because a row pinned between the prune computing its id list and executing the delete is not protected. (4) **The table is bounded by its PRIMARY KEY, not a sweep**: one row per region, `INSERT OR REPLACE`, so there is no growth curve to get wrong.
- **`calendar_snapshot` (2026-08-26) is the same pattern with two differences that matter.** Twelve months of ranked popular releases, **per region in use**, built once a day; `candidatesForMonth` reads memory cache → table → provider, and every consumer (the calendar app, the public month pages, Home's Upcoming rail) gets it with no call-site change. Measured: paging 11 months went 10.4 s / 33 provider calls → **1.3 s / 0**, a cold month 1.24 s → **12–20 ms**, and `/calendar/2026-09` went from **8 of 15 linkable items to 15 of 15** (it persists with a null user by design, so anything we did not already hold was dead text on an indexed page). ⚠️ **(a) IT CAN GROW WHERE `home_snapshot` CANNOT**: that one is keyed by region alone so `INSERT OR REPLACE` bounds it structurally; this one is keyed by region AND month over a SLIDING window, so the build must delete out-of-window months and out-of-use regions, and a test asserts it. ⚠️ **(b) THE WINDOW IS −5..+6, NOT ±5**: `indexableMonths()` advertises +6, and a five-month future window would leave a crawlable, sitemap-listed month falling back to a live fan-out with nothing to surface it; a test asserts the snapshot window stays a **superset** of the indexable one. Layer 3 stays because the servable range is ±12 and a shared link into an outer month must not rot.
- **A snapshot built for `DEFAULT_COUNTRY` only can measure as working and still fix nobody.** (2026-08-26.) The calendar snapshot's first version copied `home_snapshot` and built one region. Every test passed and the anonymous path genuinely was fixed, so the change read as done. - **Five SEO decisions that read as tidy-able and are not.** All 2026-08-20, all in `docs/seo.md`.
  - **`aggregateRating` must stay OUT of the item-page JSON-LD** (`src/lib/jsonLd.ts`, with a test asserting its absence). - **Module-level state in `src/lib/` is NOT process-global — Next resolves a module into a different bundle per route kind, so `new Map()` at module scope becomes SEVERAL maps.** Proven on prod 2026-08-20 with the same cold-month workload down each path: a PAGE route's provider calls never moved the counters an API route had just moved. Measure before believing it. → `docs/scalability.md`
- **Provider cost scales with CATALOG BREADTH × CRAWLER APPETITE, not with pageviews — and the quota is the ceiling, not compute.** Measured 2026-08-20 via `/api/health`'s new `providerCalls`: a cold `/tag/{genre}` page costs **14 provider requests, 4 of them RAWG**, a cold `/calendar/{month}` costs 5, a warm facet page and the homepage cost **0**. - **Erasure is schema-derived, and a `user_id` column is what makes a table personal.** `deleteAccount()` (`src/lib/account.ts`, H4.6) finds its targets by reading `sqlite_master` for tables with a `user_id` column, deletes them explicitly (never trusting `ON DELETE CASCADE`, which is a silent no-op without `foreign_keys = ON`), and re-checks completeness inside the transaction. So: a new user-scoped table is covered the moment it exists — but **only if its owning column is literally named `user_id`**. Name it anything else and GDPR erasure silently skips it with every test still green. Same rule in the other direction for `/api/account/export`: it uses explicit column lists, never `SELECT *`, so credentials can't drift into a file the user downloads — a new user-scoped table needs a block added there **by hand**, unlike erasure. - **A `@theme` custom property that is only ever read through inline `var()` is TREE-SHAKEN by Tailwind v4 — it resolves to an empty string at runtime, silently.** No build error, no lint error, no failing test; the declaration it feeds is simply invalid and the element inherits instead. Bit `--color-facet-*` on the day they were added (2026-07-30): every facet chip rendered in inherited text colour. **`--color-media-game/-movie/-show` had the same latent bug and were relocated to a plain `:root` block on 2026-07-31** — components still read `TYPE_COLORS` from `constants.ts` rather than the token (harmless now, no reason to migrate). Rule: if a token is only consumed as an inline style value, declare it in a **plain `:root` block** (as the named `--space-*` steps already are), not `@theme`. This is a *second*, distinct `@theme` trap in `globals.css` — the first is the spacing-namespace collision noted at `--spacing`. Quick check: `getComputedStyle(document.documentElement).getPropertyValue('--your-token')` returning `""` means tree-shaken, not mistyped.
- **A design token's `@theme` prefix must be the utility's OWN theme key, and a wrong prefix generates NO RULE AT ALL — not a wrong value, nothing.** *Third* `@theme` trap in `globals.css`, and a different mechanism from the tree-shaking one above: the token is emitted and resolves perfectly, but the short-name utility it was meant to feed never exists, so the class is inert and the element silently keeps the built-in default. Motion tokens were declared `--duration-instant/-fast/-base/-slow` from 2026-07-23 to 2026-08-14; Tailwind v4's `duration-*` utility resolves named values from **`--transition-duration-*`**, so `duration-base` matched nothing and ~28 call sites across 10 files ran at Tailwind's default **150ms instead of the design's 80/120/200/320ms**. Nothing catches it — `tsc`, `npm run lint`, 677 tests and `next build` were all clean, `getComputedStyle(document.documentElement).getPropertyValue('--duration-base')` returned `.2s` (so the tree-shaking check above says "healthy"), and an unrecognized utility class is not an error in any tool. Fixed by renaming the tokens, which made all 28 short names work as-is. Note `--ease-*` was correct all along — that IS the v4 namespace, where the built-in `--ease-in`/`--ease-out` live.
  - **Before inventing a token prefix, read the utility's actual theme key** — `grep -o '"duration",[^;]\{0,300\}' node_modules/tailwindcss/dist/lib.js` prints `valueThemeKeys:["--transition-duration"]`. Don't infer the namespace from the utility name; several don't match.
  - **Verify a utility by looking for a matching RULE, not by resolving the token** — the token resolving proves nothing here. Fetch the stylesheet and grep it: `(await (await fetch(document.querySelector('link[rel=stylesheet]').href)).text()).match(/\.duration-[a-z]+\{[^}]*\}/g)`, then confirm `getComputedStyle(el).transitionDuration` on a real element reads the intended value.
  - ⚠️ **A naive `document.styleSheets` walk gives a FALSE NEGATIVE and is how this was nearly mis-scoped.** Chrome gives every `CSSStyleRule` an empty `.cssRules` (CSS nesting), so the obvious recursive walk — `if (r.cssRules) { walk(r.cssRules); continue }` — skips every leaf rule and reports zero matches *whether or not the fix landed*. Test `selectorText` first, and only recurse when `r.cssRules.length > 0`.
  - Tailwind is scan-based, so a token with no call site emits no rule. "No rule" only means a bug when something actually *uses* the class — and a class injected at runtime was never scanned, so it can never be tested that way.

Writing `duration-instant` / `ease-standard` into this file and `docs/archive/history.md` is why prod's stylesheet carries those two rules while nothing in `src/` uses them. Harmless at ~200 bytes and the tokens are real, but don't read "the rule exists in prod" as proof a component uses it, and expect doc prose to move the CSS output.

## Model/agent routing for this repo

The main session's model is whatever the human picked — this doesn't change that. It guides which model/agent tier to reach for when *delegating* via the Agent/Task/Workflow tools:

- **Bulk file search / "where is X" exploration** → the `Explore` agent at the default model. Cheap, fast, keeps the main context clean.
- **Mechanical doc maintenance** (archiving a finished phase, reformatting, renaming) → fine to delegate at low effort. Low blast radius, easy to review the diff afterward.
- **Anything touching `migrations.ts`, `matcher.ts`'s write paths, sync/pull adapters, or auth/session code** → do NOT delegate to a background/low-effort agent. These carry the invariants above (a mistake risks data loss or an auth hole) — do this work in the main loop at full effort, and verify against real `data/rr.db` behavior rather than trusting green tests alone (see [[db-migrations-and-testing]]: every DB test starts fresh, so none of them exercise the upgrade path production actually takes).
