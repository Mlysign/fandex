## Verifying anything behind a login

`/insights`, `/profile` and `/settings` `router.replace("/")` for anonymous visitors; `/library` and `/wishlist` render a sign-in gate instead (2026-08-18) and the item-detail personal block swaps to its anon controls. Either way **the real content can't be checked without a session.** Use **`GET /api/dev/login`** — it mints one for the `users.id` in `DEV_LOGIN_USER_ID` and redirects to `/`; the local `.env` already points at the real account. Works in the in-app browser pane.

Don't hand-mint a JWT (the harness blocks it as credential-forging, correctly) and don't assume anon-only verification is the best available — that assumption is why several batches shipped "not yet verified logged-in". **Never call `/api/auth/logout` to test the anon side**: it bumps `session_epoch` and kills Nils's own browser session, which only a real OAuth round-trip restores.

The route's three fail-closed gates (`NODE_ENV !== "production"` · loopback host · a real identity row) are what keep it off fandex.org. Do not relax them, and treat it as auth code — main-loop only, per the routing rules below.

## Load-bearing invariants (don't relearn these the hard way)

- **The prune invariant:** a sync pull that fails must THROW, never return `[]`/partial. `syncProvider` (`src/lib/sync/index.ts`) deletes every local entry missing from a successful pull, so a swallowed error silently wipes the user's library. When adding any adapter: a pull that can't complete must throw; a pull that legitimately found nothing may return `[]`. **Anything a pull carries beyond ids inherits this** — MB14's per-episode state rides on Trakt's existing library pull precisely so it can't diverge, and its reconcile sits INSIDE `syncProvider`'s try, after the pull, so an outage is a no-op instead of a wiped watch history. Corollary for any optional per-item payload: **`undefined` and `[]` must mean different things** — "this pull says nothing about X" vs "this pull is authoritative about X and there is none". Conflating them is how an empty pull deletes data. A declared capability (`capabilities.episodes.read`) is the gate, never a sniff of the returned shape.
- **A component that renders `null` when empty must know WHY it is empty before it ships.** Twice in one day (MB14's Home rail and its item-page twin): each returned `null` for four unrelated states — no data yet, the provider pull is FAILING, still filling a cache, genuinely caught up — so a real, diagnosable problem read as "the feature doesn't work" with nothing to go on, and the person looking at it was on a phone with no console. `return null` on an empty state is not a neutral default; it is a decision to discard the only evidence anyone will get. The fix both times was the same: a `*Status`/`*Diagnostic` function returning the counts that separate the cases (computed independently, so a throw in the main path can't take the explanation down with it), a provider write logging the SHAPE of what it pulled and not just what it stored, and one line of copy that never claims success it cannot see.
- **A new table referencing `media_items` must be added to `dbPrune.ts`'s `PRUNABLE_WHERE`.** The boot prune is **default ON in prod** and deletes `browsed = 1` catalog rows nobody "acted on" — where acted-on is a hard-coded list of the tables that cascade off `media_items`. MB14's `user_episode_state` was the fourth: ticking episodes writes none of the other three, so a show tracked but never rated or saved stays `browsed = 1`, and without the clause the next deploy would have cascaded that watch history away. The predicate's own comment already says why it names tables rather than trusting one to be a superset — extend the list, don't reason about whether it's implied.
- **An AGE cap is not a SIZE cap, and a boot-only sweep is not a schedule.** `facet_page_cache` shipped 2026-08-13 with a 24 h TTL swept once per boot at 2000 rows, and by 2026-08-19 held **24,953 rows / 222.8 MB — 80.2% of a 331 MB database** that had measured 37.7 MB the day before it landed. Two independent holes. (1) Prod runs for **days**, so a boot-only sweep never ran; anything expiring in-process expired only in theory. (2) The writer is somebody else's **crawler** walking the person/tag/studio long tail, so inside one TTL window every row is "fresh" by definition and the age sweep had nothing to collect while the table grew all day. Nothing catches this: tests, `tsc`, lint and the build are all green, `/api/health` reports the file size but not what is in it, and it surfaces as **container memory** (cgroup v2 bills page cache, and page cache tracks FILE SIZE) rather than as a database problem. Rules that came out of it: **any table written on a request path needs a row or byte ceiling, not just a TTL**; **run the bound on an interval, unref'd, in bounded batches** (better-sqlite3 is synchronous and Litestream holds a second connection); **evict by write time, not read time** — tracking reads turns every cache HIT into a write, which is the shape that caused this; and **deleting rows does not shrink the file** — the pages go on the freelist, so reclaiming needs a `VACUUM`, which needs the exclusive lock, which is only available **before Litestream attaches** (`VACUUM_ON_BOOT=1` in `docker-entrypoint.sh`; it truncates the WAL as a side effect, and may or may not start a new Litestream generation — a 2026-07-21 VACUUM taken *with* Litestream attached was absorbed into the existing one). → [[prod-incidents]]
- **A provider's response SHAPE is not verifiable from its documentation, and a mocked test of an assumed shape proves nothing.** Trakt documents `/sync/watched/shows` as returning `seasons` by default (only `?extended=noseasons` suppresses it). It **does not** — `seasons` is **absent**, not empty, on all 280 entries, with `?extended=full`, plain+paginated, and plain+unpaginated (which also silently returned **100 of 280**, so it is paginated too). MB14 shipped reading episodes off that response and attached **zero** for four deploys; a run-time fallback grafting seasons from the plain call hit a second empty well; and the unit test asserting the graft worked **passed**, because it mocked the shape the docs implied. `tsc`, `npm run lint`, **750 tests** and `next build` were green throughout. The fifth deploy added a shape probe (`/api/dev/trakt-shape`) instead of another inference and answered it in one call. **When a provider integration returns nothing, probe the payload before theorising about the code** — and prefer a check the environment can actually run (a call count) over asserting a payload you had to invent. Episodes come from **`/sync/history/episodes`** (bulk, one entry per play → dedupe) or **`/shows/{id}/progress/watched`** (per-show; ⚠️ lists every aired episode, so only `completed: true` counts). → [[trakt-episode-endpoints]]
- **Per-source FAILURE isolation is not per-source LATENCY isolation, and the breaker must THROW.** Every provider adapter try/catches, so one dead source never *broke* a page — but the caller still *waited* for it. RAWG going down (Cloudflare 522, ~19.8 s) × `http.ts`'s two 5xx retries = ~60 s per call; `fetchPages` fires 5 pages under one `Promise.all` and `/api/home` reaches RAWG twice, so a cold `/api/home` measured **2.2 minutes** (2026-08-02). `http.ts` now has a per-host circuit breaker + an optional `budgetMs`; browse paths pass `BROWSE_BUDGET_MS`, **sync/pull deliberately keeps its unbounded budget**. **The breaker throws `ProviderUnavailableError` and must never fabricate a Response** — a synthetic 503 would need zero call-site changes and would ALSO be read as `!res.ok` by the pull adapters, turning an outage into an empty library under the prune invariant above. Browse code opts into degradation explicitly (`bestEffort` in `discoverFeed.ts`); pull code keeps throwing. Also: **measure before optimising** — the 58 s cold Discover load was blamed on the catalog pool cache for days; the pool rebuild is ~430 ms (`scripts/probe-pool.mjs`), and the 58 s was entirely this.
- **If a medium has two providers, a single-source pull is a bug — and the surfaces disagree by default.** Games are served by RAWG *and* IGDB. `personalizedFeed` pulled both; three other paths pulled RAWG alone, and nobody noticed until RAWG actually went down (2026-08-02) and those three lost the entire media type while the feed beside them carried on: the games **load-more** returned `[]` forever with the button still enabled (a silent dead control), `/api/discover`'s **cold-start/anonymous** branch left logged-out visitors with no games at all while signed-in ones were fine, and `/api/home`'s trending rail dropped every game so the whole "Popular right now" section vanished under the Games filter. The dual-source pull now exists ONCE (`fetchGamePageAllSources` / `fetchTrendingGames` / `dedupeGames` in `discoverFeed.ts`) — one correct copy plus three single-source ones is exactly how they drifted. When touching any games surface, check **all** of them: initial browse, load-more (a *different* code path from the browse), trending, calendar-popular, profile. And test the invariant that matters — *a games pull survives one source being down* — not the happy path, which passed throughout the outage.
- **The thin-write / pool rule:** a discover-time write is insert-only and stamps `browsed=1` / projection version `0` — it must never overwrite or degrade a real synced/ingested row.
- **Migrations have TWO apply paths** — in-process via `getDb()` (what tests/prod use) and standalone via `node scripts/migrate.mjs` (plain Node, resolves neither the `@/*` alias nor extensionless specifiers). Green tests only prove the in-process path. After touching `migrations.ts`, run the standalone script against a DB copy.
- **`db.ts`'s `CREATE TABLE`/`CREATE INDEX` block runs BEFORE migrations** and must stay valid against an OLD (pre-migration) schema. A column added by a migration must have its index created in that *same* migration, never in the schema block — putting them together only works on a fresh DB and silently breaks every upgrade path.
- **Any route reading an env var to build an absolute URL (`BASE_URL`, etc.) must export `dynamic = "force-dynamic"`.** Next prerenders route handlers without it at `next build` time, and Railway's build-phase env can differ from its runtime env (confirmed: `NEXT_PUBLIC_BASE_URL` resolves correctly at runtime but wasn't available at build) — the wrong value gets baked into the static output permanently, invisible until you actually read the response body (status 200 either way). `sitemap.ts` had this from the start; `robots.ts` didn't and shipped `localhost:3000` to prod until a live smoketest caught it (SM7, 2026-07-19). `/legal/[locale]/[doc]` (H4.1, 2026-07-30) is the same trap: `generateMetadata` builds canonical + hreflang URLs from `BASE_URL`, so it needs the export too — verify with `npm run build`'s route table showing `ƒ (Dynamic)`, not `○ (Static)`.

- **Erasure is schema-derived, and a `user_id` column is what makes a table personal.** `deleteAccount()` (`src/lib/account.ts`, H4.6) finds its targets by reading `sqlite_master` for tables with a `user_id` column, deletes them explicitly (never trusting `ON DELETE CASCADE`, which is a silent no-op without `foreign_keys = ON`), and re-checks completeness inside the transaction. So: a new user-scoped table is covered the moment it exists — but **only if its owning column is literally named `user_id`**. Name it anything else and GDPR erasure silently skips it with every test still green. Same rule in the other direction for `/api/account/export`: it uses explicit column lists, never `SELECT *`, so credentials can't drift into a file the user downloads — a new user-scoped table needs a block added there **by hand**, unlike erasure. And the rule runs both ways: a CATALOG table must NOT have a `user_id` (MB14's `show_seasons`/`show_episodes` deliberately don't), or erasure starts deleting shared metadata.

- **A `@theme` custom property that is only ever read through inline `var()` is TREE-SHAKEN by Tailwind v4 — it resolves to an empty string at runtime, silently.** No build error, no lint error, no failing test; the declaration it feeds is simply invalid and the element inherits instead. Bit `--color-facet-*` on the day they were added (2026-07-30): every facet chip rendered in inherited text colour. **`--color-media-game/-movie/-show` had the same latent bug and were relocated to a plain `:root` block on 2026-07-31** — components still read `TYPE_COLORS` from `constants.ts` rather than the token (harmless now, no reason to migrate). Rule: if a token is only consumed as an inline style value, declare it in a **plain `:root` block** (as the named `--space-*` steps already are), not `@theme`. This is a *second*, distinct `@theme` trap in `globals.css` — the first is the spacing-namespace collision noted at `--spacing`. Quick check: `getComputedStyle(document.documentElement).getPropertyValue('--your-token')` returning `""` means tree-shaken, not mistyped.
- **A design token's `@theme` prefix must be the utility's OWN theme key, and a wrong prefix generates NO RULE AT ALL — not a wrong value, nothing.** *Third* `@theme` trap in `globals.css`, and a different mechanism from the tree-shaking one above: the token is emitted and resolves perfectly, but the short-name utility it was meant to feed never exists, so the class is inert and the element silently keeps the built-in default. Motion tokens were declared `--duration-instant/-fast/-base/-slow` from 2026-07-23 to 2026-08-14; Tailwind v4's `duration-*` utility resolves named values from **`--transition-duration-*`**, so `duration-base` matched nothing and ~28 call sites across 10 files ran at Tailwind's default **150ms instead of the design's 80/120/200/320ms**. Nothing catches it — `tsc`, `npm run lint`, 677 tests and `next build` were all clean, `getComputedStyle(document.documentElement).getPropertyValue('--duration-base')` returned `.2s` (so the tree-shaking check above says "healthy"), and an unrecognized utility class is not an error in any tool. Fixed by renaming the tokens, which made all 28 short names work as-is. Note `--ease-*` was correct all along — that IS the v4 namespace, where the built-in `--ease-in`/`--ease-out` live.
  - **Before inventing a token prefix, read the utility's actual theme key** — `grep -o '"duration",[^;]\{0,300\}' node_modules/tailwindcss/dist/lib.js` prints `valueThemeKeys:["--transition-duration"]`. Don't infer the namespace from the utility name; several don't match.
  - **Verify a utility by looking for a matching RULE, not by resolving the token** — the token resolving proves nothing here. Fetch the stylesheet and grep it: `(await (await fetch(document.querySelector('link[rel=stylesheet]').href)).text()).match(/\.duration-[a-z]+\{[^}]*\}/g)`, then confirm `getComputedStyle(el).transitionDuration` on a real element reads the intended value.
  - ⚠️ **A naive `document.styleSheets` walk gives a FALSE NEGATIVE and is how this was nearly mis-scoped.** Chrome gives every `CSSStyleRule` an empty `.cssRules` (CSS nesting), so the obvious recursive walk — `if (r.cssRules) { walk(r.cssRules); continue }` — skips every leaf rule and reports zero matches *whether or not the fix landed*. Test `selectorText` first, and only recurse when `r.cssRules.length > 0`.
  - Tailwind is scan-based, so a token with no call site emits no rule. "No rule" only means a bug when something actually *uses* the class — and a class injected at runtime was never scanned, so it can never be tested that way.
  - **The scanner reads MARKDOWN too, and `@import "tailwindcss"` here has no `@source` scope** — so it walks the whole project (minus gitignored paths) and extracts candidates from prose. Writing `duration-instant` / `ease-standard` into this file and `docs/archive/history.md` is why prod's stylesheet carries those two rules while nothing in `src/` uses them. Harmless at ~200 bytes and the tokens are real, but don't read "the rule exists in prod" as proof a component uses it, and expect doc prose to move the CSS output.
- **CSS visibility is not conditional rendering.** A `lg:hidden` tree plus a `hidden lg:block` tree puts BOTH in the DOM, so every client island in them mounts twice — measured on the item page (2026-07-30): `PersonalSection` fired **two `/api/detail` round-trips per view** and the trailer `<iframe>` loaded two YouTube players, one invisible. Switch the *layout* with CSS and render the CONTENT once; 1,239 → 723 DOM nodes on that page. (Paired title/nav elements where one is `display:none` are fine and deliberate — that removes it from the a11y tree — but they must be static markup, not whole subtrees with effects.)
- **"The nav reaches every page" is not the same claim for every session state.** H4.1 (2026-07-30) put `LegalFooter` at the bottom of `/profile` only, reasoning that `AppNav`'s "You" slot makes `/profile` reachable from anywhere — true for a **logged-in** visitor, false for an **anonymous** one. `AppNav.tsx`'s "You" slot renders as a button that opens `SignInDialog` for anon (`authed === false`), not a link to `/profile` at all, and `ProfilePageClient.tsx` additionally `router.replace("/")`s an anon visitor before the footer ever renders even on a direct URL hit. Found by H4.10's compliance review (2026-08-02): **no anonymous visitor can reach any `/legal/*` page through the app's UI.** Low-stakes while the Impressum stays a noindexed placeholder, but the two-click BGH rule genuinely fails once H4.2 ships real content — check this before treating H4.2 as done. General lesson: when a UX claim depends on "the nav gets you there," verify it separately for every auth/session branch the nav itself renders differently for, not just the one you tested.

- **An auth gate must ASK, never disappear.** A gate that `router.replace("/")`s, returns `null`, or renders inert "sign in to…" text is indistinguishable from a broken feature — and the person hitting it is by definition the one least able to diagnose it. Six of these shipped at once and were all found in one logged-out session (2026-08-18): `/calendar` and `/wishlist` bounced home, the nav search box was totally inert (its vocab endpoint was `withUser`, so the dropdown never opened and Enter had no options to pick from), a third of Home's cards dropped their action bar entirely, and the item page's "Sign in to see your Fandex Score" was a static div. Nothing crashed, nothing 500'd, every test was green. Corollary that fixed half of them: **before gating a surface, ask which part of it is actually per-user** — the calendar's Popular scope is provider-fed with no user data in it, and a card's "sign in" prompt needs no item identity, so both were gating the wrapper rather than the data. `withOptionalUser` (`src/lib/withUser.ts`) is the wrapper for a route serving both; it hands the handler `session | null`, which `persistDiscoverBatch` still uses as the PR15 write gate — **pass the null through, never a placeholder id**. Its `anonLimit` must be sized to what the route SPENDS (240/min default for a local read; **60** for `/api/calendar/popular`'s provider fan-out) — too tight is a live bug, since the nav search fires two requests per debounced keystroke. → [[anon-gates-must-ask-not-bounce]]
- **Platform colour-coding is removed site-wide (Nils, 2026-08-18) — identify a provider by its LOGO, via `<BrandGlyph source="steam">`, not its hex.** No brand hue in ANY state, hover included; hover is the house treatment. **`TYPE_COLORS` (game/movie/show) is a different axis and stays.** Size the mark for the worst case: simple-icons ships WORDMARKS (IGDB, Wikipedia) that are illegible below ~20px, which is why `StoreLink` drops its chip and renders the bare mark at 22px. → [[platform-brand-marks-not-colours]]
- **Two reasons a control can have no hover feedback, and one reason a working hover LOOKS broken.** (1) Tailwind v4's preflight leaves `<button>` at the browser's `cursor: default` — every button in the app was missing the pointer until a `@layer base` rule in `globals.css` fixed it once; a per-component fix never finds this. (2) **A `hover:bg-*` utility cannot beat an inline `style={{ background }}`** — the class is in the DOM and the rule is in the stylesheet and it still does nothing. Put the VALUES in custom properties and let utilities switch them (`QUICK_BTN_CLASS` + `quickBtnVars`, `ActionCells.tsx`). (3) ⚠️ **A Browser pane that isn't displayed stops compositing, so transitions never advance and `getComputedStyle` returns the START value of every transitioned property** while `matches(':hover')` says `true` — a correct hover measures as dead through `!important` and a literal `red`. Inject `* { transition: none !important }` before measuring. → [[hover-and-cursor-traps]]

- **A `//` comment in JSX CHILDREN position is a TEXT NODE and renders on the page.** Not a typo class — a *refactoring* class: wrapping an existing `return ( … )` in a fragment or a new parent silently moves any `//` comment inside it from JS position (legal, invisible) to JSX-children position (visible text). It happened in `LegalLinks.tsx` on 2026-08-03 and put a whole paragraph of tap-target notes into the site footer, with **`tsc` clean, 540 tests passing, `npm run lint` 0 errors and `next build` clean** — it is valid JSX, so nothing but a human looking at the page caught it. `react/jsx-no-comment-textnodes` is now an **ERROR**. In JSX children always `{/* … */}`, never `//`, and re-check every comment inside a `return` you just wrapped. This is the *second* JSX-comment incident here — see the `eslint --fix` note below. → [[jsx-comment-in-children-renders]]

Affiliate decoration runs ONLY at the two detail boundaries (`/api/detail`, `lib/detail/publicDetail.ts`) via `decorateItemLinks()` — never in `normalize.ts` (baking tags into stored projections would need a `PROJECTION_VERSION` bump + full-catalog re-projection, the op that took prod down) and never in `mergeLinks()` (hot path, renders no links). Every link must stay a **direct outbound `<a href>`**: a Fandex-hosted redirect or click pixel breaks §25 TDDDG's cookie exemption *and* Amazon's terms at once. → [[monetization-h3]]
- **A type-only import must be written `import type` — enforced as an eslint ERROR (`consistent-type-imports`, 2026-07-30).** Not style: Node's native type-stripping (what `scripts/alias-hooks.mjs` gives every `rehearse-*.mjs`/`calibrate-*.mjs`) erases only *syntactically* type-only constructs, so a plain `import { Foo }` where `Foo` is an interface throws `SyntaxError: does not provide an export named 'Foo'` the moment a standalone script reaches that module — while tsc, vitest, `next dev` and `next build` all elide it correctly and report nothing. Every export of `src/types/index.ts` is type-only. **And: do not run `eslint --fix` broadly without diffing for non-import changes** — it rewrote three `{/* eslint-disable-next-line */}` JSX comments in `AuthOptions.tsx` to a bare `{ }`, destroying the directives while looking inert (both render nothing).
- **`npm run lint` scans the whole cwd with no path filter — a stray `git worktree` under `.claude/worktrees/` (from an `isolation:"worktree"` agent run) gets scanned too, gitignored or not.** `eslint.config.mjs`'s `globalIgnores` excludes `.claude/worktrees/**` explicitly now (2026-07-30), after an abandoned worktree from an unrelated prior session — checked out at an old commit, predating a since-added lint rule — surfaced 200+ false "errors". If `npm run lint` ever reports a wall of errors you don't recognize, check `git worktree list` before assuming you broke something; never delete a worktree you didn't create without checking first, it may be another session's in-progress work.
- **The `react-hooks/*` eslint rules are ERRORS here, and the repo is error-clean.** Some remaining `set-state-in-effect` flags are on genuinely idiomatic patterns (storage hydration, prop→state sync, data-fetch-on-mount, load guards, layout measurement) and carry justified `eslint-disable-next-line` comments — those are correct as-is, not bugs to fix. Don't remove a disable comment without checking why it's there first.

## Model/agent routing for this repo

The main session's model is whatever the human picked — this doesn't change that. It guides which model/agent tier to reach for when *delegating* via the Agent/Task/Workflow tools:

- **Bulk file search / "where is X" exploration** → the `Explore` agent at the default model. Cheap, fast, keeps the main context clean.
- **Mechanical doc maintenance** (archiving a finished phase, reformatting, renaming) → fine to delegate at low effort. Low blast radius, easy to review the diff afterward.
- **Anything touching `migrations.ts`, `matcher.ts`'s write paths, sync/pull adapters, or auth/session code** → do NOT delegate to a background/low-effort agent. These carry the invariants above (a mistake risks data loss or an auth hole) — do this work in the main loop at full effort, and verify against real `data/rr.db` behavior rather than trusting green tests alone (see [[db-migrations-and-testing]]: every DB test starts fresh, so none of them exercise the upgrade path production actually takes).
