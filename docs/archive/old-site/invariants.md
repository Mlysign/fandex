# The old site's invariants (archived 2026-10-23)

The Next.js site (`src/app`, `src/components`, most of `src/lib`, the Dockerfile, Litestream) was
deleted on 2026-10-23, after running nowhere since Railway went on 2026-10-05. These are the
rules from `AGENTS.md` that protected only that code, moved here word for word. They matter
again only if old code is brought back. The code itself is at the git tag `old-site-final`
(`git worktree add ../fandex-old-site old-site-final`, then `npm ci` there, to run it as the
visual reference `docs/app-parity.md` asks for).

File and memory names below point at what existed then. Most of the files are gone; the
memory files are not.

## Data, sync, and the database

- **Check sync staleness PER PROVIDER, never with one collapsed `Math.max`.** A Trakt-only run made Steam look fresh and froze it for three weeks. `staleProviders()` in `syncClient.ts` is the only decider; `syncToCompletion()` takes a LIST. ⚠️ An empty list must be an explicit no-op: `/api/sync` falls back to the whole registry on an empty `providers`. → [[trakt-sync-completeness]]
- **An identity provider that holds no library must be listed in `IDENTITY_ONLY_PROVIDERS` (`syncClient.ts`).** `staleProviders()` reads "no `sync_log` row" as "overdue", which is right for a provider that CAN sync and permanently wrong for one that cannot: it reads as due forever and fires a doomed sync on every `/library` load, silently. ⚠️ **`AuthProvider` (can log you in) is a SUPERSET of `Source` (a place media comes from)** and the two must not be collapsed: putting `google` in `Source` would make it legal for a store link, a release date and an `/api/sync` target. → [[identity-only-auth-providers]]
- **Migrations have TWO apply paths**: in-process via `getDb()` (tests + prod) and standalone via `node scripts/migrate.mjs` (plain Node; resolves neither the `@/*` alias nor extensionless specifiers). Green tests only prove the first. After touching `migrations.ts`, run the standalone script against a DB copy. → memory `old-site/db-migrations-and-testing.md`
- **`db.ts`'s `CREATE TABLE`/`CREATE INDEX` block runs BEFORE migrations** and must stay valid against the OLD schema. A column added by a migration gets its index created in that *same* migration. Putting them together works on a fresh DB and silently breaks every upgrade path.
- **Any SQL reaching the SCHEMA must parse on the SQLite LITESTREAM embeds (~3.40), not the 3.53 `better-sqlite3` ships.** SQLite parses the whole schema before preparing any statement, so one unsupported construct stops the backup daemon dead while every test, the build and `/api/health` stay green. Express sorting as `ORDER BY` in a SUBQUERY, never inside an aggregate's argument list. Check new schema SQL with an OLD `sqlite3` CLI against a DB copy, and re-run the restore drill after any schema change. → memory `old-site/prod-incidents.md`
- **`user_library` / `user_watchlist` are VIEWS**, and a `CREATE INDEX` on either kills the next boot. → memory `old-site/cache-tables-are-views.md`
- **A new table referencing `media_items` must be added to `dbPrune.ts`'s `PRUNABLE_WHERE`.** The boot prune is default ON in prod and deletes `browsed = 1` rows nobody "acted on", where acted-on is a hard-coded table list. Extend the list; don't reason about whether one table implies another.
- **Any table written on a REQUEST path needs a row or byte ceiling, not just a TTL**, run on an unref'd interval in bounded batches, evicting by WRITE time (tracking reads turns every cache hit into a write). An age cap is not a size cap and a boot-only sweep is not a schedule: prod runs for days, and a crawler keeps every row inside the TTL window while the table grows all day. Deleting rows does not shrink the file, but `db.ts` VACUUMs after any migration applies, so you rarely need to act. → memory `old-site/prod-incidents.md`
- **The pool PATCHES a content change; it must stay EXACTLY equal to a rebuild.** `unfoldEntry` un-counts an item's vocab with the RAW pre-alias facets it was folded with (`_cache.rawFacetsById`); post-alias ones are a different set. A vocab that is merely close is not a small bug — `computeIdf` reads those counts, so every ranking shifts silently. Every check runs BEFORE any mutation, and a throw is answered with a rebuild. ⚠️ The changed set is `updated_at >= prevMx`, never `>`: one-second resolution means `>` misses a write. ⚠️ A DELETION still rebuilds (which row went is unknowable from an aggregate). → `docs/archive/history.md` (catalog growth §16)
- **A same-length payload rewrite inside one second is invisible to the facet cache**, whose token is `(last_synced, OCTET_LENGTH)`. Swapping a nine-byte genre for another nine-byte genre serves the OLD derivation, correctly. Know this before blaming code: it cost an hour once, in a test fixture. Likewise `contentSignature` cannot see a same-second re-sync at all (neither COUNT nor MAX moves) — the 5-minute pool TTL is what covers that, and any test of a re-sync must bump `updated_at` by hand.
- **A helper that signature-checks its cache must be called once per PASS, never once per item.** `computeFandexScore` called three such helpers per item, so **79% of Fandex Score CPU was cache validation**. `scoringContext()` fetches them once: **5.1×**, byte-identical. Any loop over the catalog wants the same. → `scripts/probe-score.mjs`
- **A cache KEY must be cheaper than the thing it guards, and it must never touch a VIEW.** `librarySignature` asked `user_library` (a view of CTEs, `json_group_array` and two GROUP BYs) for a COUNT and a MAX: **69 ms per call, three calls per request**, to produce a cache key. Off the base table, with a covering index, it is **1 ms** — and `find()` went 190 → 86 ms. Sign off `user_item_state`; a per-source count is strictly more sensitive than a per-item one, and a signature only has to CHANGE. → `docs/archive/history.md` (catalog growth §11)
- **A memory fix sized from `JSON.stringify` length is sized wrong.** `poolWeight()` said the scoring pool was the biggest thing in memory; measured RETAINED heap says it is **13.5 MB of 109.6**, and `facetCache.derived` was 86 MB. The planned facet-string interning, at its theoretical best (130,737 occurrences → 22,341 objects, 5.85× reuse), saved **0.4 MB**. Serialised bytes are a growth RATE, never a target list. Measure with `node --expose-gc scripts/probe-memory.mjs`. → `docs/archive/history.md` (catalog growth §13)
- **Price a cache ENTRY before choosing its bound, and never store a field no caller reads.** `facetCache` stored `sources[].data`, the whole parsed provider blob: **76% of a 25.5 KB entry**, making its `max: 6000` a ~200 MB ceiling. Two routes had been dropping that field on the WIRE for a month while the process held the same bytes. Make the TYPE exclude it so `tsc` is the proof. → `docs/archive/history.md` (catalog growth §13)
- **A token computed in BOTH SQL and JS must be UTF-8 BYTES** (`OCTET_LENGTH` / `Buffer.byteLength`). SQLite's `LENGTH()` counts code points, JS `.length` counts UTF-16 units, so any payload with an emoji made facetCache's freshness key unmatchable: **56 of 7,006 links never once hit that cache**, invisibly, since a permanent miss only costs time. `LENGTH()` on TEXT also has to decode the string — **67–84 → 8–12 ms** over the pool. → `facetCacheFreshnessToken.test.ts`
- **A cache key that encodes a WRITE-mode flag must be filled for BOTH modes by the writing build.** `publicFacetDetail`'s key carries `persist`, correctly (it changes which items are linkable), so the two flags own separate entries, and a persisting build that fills only its own leaves every crawler on the pre-write payload for the full 24 h TTL. Writing the same object under the other key is exact, not an approximation: once the rows exist, `lookupExistingUuids` resolves what `persistDiscoverItems` just wrote. ⚠️ ONE DIRECTION ONLY: a `nopersist` build must never fill the `persist` entry, or a later persisting caller skips the write. → `docs/seo.md`
- **A cached array indexed by POSITION may be served stale, never misaligned.** `fandexScoresFor` serves the previous scores while a chunked pass refreshes them, so no request scores the catalog; that is only safe because `poolSig` is tracked apart from `sig` ("index *i* still means `vectors[i]`" is a different question from "these numbers are current") and a moved pool is REMAPPED by id, with `NaN` → `fandexPending` for anything new. → `docs/archive/history.md` (catalog growth §12)
- **An item that is already a catalog row carries no `raw`, and BOTH uuid resolvers skip those** (`lookupExistingUuids`, `persistDiscoverItems`). `persistDiscoverBatch` passes a uuid `id` through for exactly this reason. Miss it and a whole page renders `linkable: false` — cards that look right and click nowhere. → `docs/archive/history.md` (catalog growth §10), memory `old-site/anon-surface-has-no-item-links.md`

## Providers, caching, and cost

- **If a medium has two providers, a single-source pull is a bug.** Games are RAWG *and* IGDB in the BROWSE feed (`fetchGamePageAllSources` / `fetchTrendingGames` / `dedupeGames`, one correct copy; three single-source ones is how they drifted). ⚠️ **The facet paths dropped RAWG entirely and that split is deliberate** — cutting it from browse too was tried and reverted the same day, and `discoverFeedSources.test.ts` fails if you retry it. When touching any games surface check ALL of them: initial browse, load-more (a *different* path), trending, calendar-popular, profile. → [[provider-latency-isolation]]
- **The discovery pool must NOT be capped** (`_cache.vectors` in `discovery.ts`, ~2.6 MB per 1,000 catalog items). It is the candidate set, so truncating it silently changes every Fandex Score, "More like this" ranking and IDF weight. Measure it (`poolWeight()`) and plan for the slope. → memory `old-site/data-model-gaps-and-plan.md`
- **Provider cost scales with CATALOG BREADTH × CRAWLER APPETITE, not pageviews, and the quota is the ceiling.** Price any new provider call on a crawlable page in cold-facet-page units via `/api/health`'s `providerCalls`. **OMDb is DELETED** (CC BY-NC at every tier; `noOmdb.test.ts` pins it out, so do not re-add) and **RAWG is off the facet paths**. ⚠️ A cold `/tag/` page should now cost 10 requests, none RAWG. That is a PREDICTION, not a measurement. → [[provider-quotas-and-scale]], `docs/scalability.md`
- **Retiring a provider means auditing every hard-coded `Source[]`, not just `SOURCES` and `METADATA`.** A bare array that omits a source silently SKIPS it, and `Source[]` is satisfied by a list naming two of six, so tsc sees nothing. `persistItem.ts`'s id-precedence list omitted `igdb`, so after the RAWG retirement every IGDB-only game resolved to null and both quick-action routes answered `400`: rating and wishlisting were dead for 310 of 1,347 games. `persistItemSources.test.ts` holds that one list to the full union. → memory `old-site/provider-retirement-hardcoded-lists.md`
- **A WAL-mode database is the `.db` PLUS its `-wal`.** Copying only the `.db` gives a pre-WAL snapshot that reads as perfectly valid and is silently stale: it reported 1,580 projection rows against the 908 actually there, because a DELETE was still in the WAL. Copy both, or every count you take is a guess. This is also why `scripts/*` probes say to point at a COPY and mean a complete one.
- **A background job's EMPTY answer is not the same as "finished", when the fetcher swallows failures.** Count consecutive empties (three) and reset on any real page. Same `undefined` vs `[]` distinction as the prune invariant; the blast radius is a lane that silently never runs again. ⚠️ **Three strikes raises the COST of a false retirement, it does not prevent one** — a quota latch is not transient, so read `exhausted: true` on a latched provider as "provider down". ⚠️ **A retired lane cannot currently be revived**: `resetBackfill()` is exported and wired to nothing. → `docs/catalog-growth.md`
- **A catalog-served card must carry every field the client SORTS on, or the control silently reorders nothing.** `voteCount: 0` becomes `communityVotes: 0`, every row ties, and a stable sort shows ARRIVAL order under a control labelled "Popularity" (the 2026-08-29 search bug again). `media_items.vote_count` / `vote_average` are denormalised for this by the SAME functions the search path uses, so the two cannot disagree. ⚠️ **This app's "popularity" IS the vote count**; do not add a provider trending metric as a second one. ⚠️ `averageCommunity` is 0-100, `voteAverage` is 0-10. ⚠️ **`ORDER BY vote_count DESC` alone pages the window BACKWARDS on a fresh DB** (SQLite sorts NULL lowest and "not computed" is NULL); lead with `vote_count IS NULL`. → `src/lib/itemStats.ts`
- **The stats refresh runs BEFORE housekeeping, and that ordering is a correctness requirement.** Housekeeping reclaims `media_links.raw_data`, the only place the votes exist, so an item blob-dropped first would sit at a stamped permanent 0. It is off the write path for a separate reason: `lookupExistingUuids` short-circuits known items into a plain SELECT so browse takes no write lock (PR13-PR15).
- **A window defined RELATIVE TO NOW cannot be filled by a one-shot sweep, because it drains while you fill it.** The backfill's `:future` lanes target the next 18 months; every lane exhausted and the counts then FELL (movie 49 → 35, show 49 → 26 in four days) as release dates passed out of the window. A target that moves needs a repeating job, not a cursor that finishes. Check whether a count is a stock or a flow before promising it will reach a threshold. → `docs/catalog-growth.md`
- **`strftime('%s','now')` has ONE-SECOND resolution, so it cannot order things within a pass.** Every backfill lane a pass touched shared one second, so "least recently run" could not separate them and one lane was hammered while five starved. Track what a pass has already used, and tie-break on DECLARATION order rather than alphabetically (which quietly re-prioritises the list). The same resolution is why `contentSignature` cannot see a same-second re-sync and why facetCache needs a length in its token.
- **Backticks inside `db.ts`'s schema template literal END THE STRING.** A SQL `--` comment written with ``identifiers`` is a parse error at the next quote, and the error points at the top of the block, not at your line. Cost two debugging rounds in one day. Write schema comments in plain prose.

## Routes, URLs, and SEO

- **Any route reading an env var to build an absolute URL must export `dynamic = "force-dynamic"`.** Next prerenders route handlers without it at build time, and Railway's build-phase env differs from runtime, so the wrong value is baked in permanently, status 200 either way. Verify in `npm run build`'s route table: `ƒ (Dynamic)`, not `○ (Static)`. → memory `old-site/railway-build-vs-runtime-env.md`
- **Any `NEXT_PUBLIC_*` read by a CLIENT component needs a Dockerfile `ARG`**. Server components still render it fine, so it looks like it worked. ⚠️ **The ARG is only half: the VALUE must exist on Railway BEFORE the build that bakes it, and setting one afterwards needs a REBUILD, not a restart.** Next inlines it as a literal at build time on the server side too, so a var added after the build reads `undefined` however many times the container restarts, and `railway variable set` does not itself rebuild. Set the variable FIRST, then deploy. → memory `old-site/next-public-env-needs-dockerfile-arg.md`
- **A client island fed by `/api/` is invisible to Google, not "probably seen":** `/api/` is under the robots `Disallow`, and Googlebot's renderer honours robots.txt for SUBRESOURCES. The fix is to pass the data in as PROPS, not to make it a server component. A client component's first render already IS server HTML. → memory `old-site/home-snapshot-and-crawlable-rails.md`, `docs/seo.md`
- **Each daily snapshot has rules that are the shape of an incident already on file.** A failed build must never replace a good one (atomic replace AFTER a validated build; clearing first turns an outage into an empty homepage). `home_snapshot_item` is in `PRUNABLE_WHERE`, and the refresh is sequenced AFTER `bootPrune` resolves. ⚠️ `home_snapshot` is bounded by its PK; **`calendar_snapshot` is NOT** (keyed by region AND month over a SLIDING window), so the build must delete out-of-window months and out-of-use regions. ⚠️ Its window is **−5..+6, not ±5**, and a test asserts it stays a superset of `indexableMonths()`. → memory `old-site/home-snapshot-and-crawlable-rails.md`
- **When a route threads a per-user parameter into a cache key, the pre-build must cover the values that parameter actually takes.** A snapshot built for `DEFAULT_COUNTRY` only passed every test and fixed nobody signed in outside it. `snapshotRegions()` reads `users.country`, capped at 8 with a log line when the cap bites. **Measure BOTH auth states.** → memory `old-site/home-snapshot-and-crawlable-rails.md`
- **Five SEO decisions that read as tidy-able and are not.** `aggregateRating` stays OUT of the item-page JSON-LD (every number we hold is someone else's; publishing it earns a SITEWIDE manual action). `robots.ts` needs BOTH `/calendar/` (allow) and `/calendar` (disallow) — longest match wins, so the SSR month pages are crawlable and the client-rendered app page is not. `/calendar/[month]` bounds its crawl surface three ways, each load-bearing. ⚠️ **A CAP APPLIED AFTER A SORT IS A SILENT FILTER**: an alphabetical genre list capped at 24 cut every game genre from a catalog that is a third games. A thin-page rule must test POOL SIZE, not LINKABLE COUNT. → [[seo-and-organic-reach]], `docs/seo.md`
- **Only the SWEPT facets go in the sitemap; do not widen it without widening the sweep.** `facetSnapshot.ts` builds a bounded set daily off the request path, and those are what `sitemap.ts` advertises. The original objection to advertising the rest still holds: thousands of `force-dynamic` fan-out URLs invite the crawl that grew `facet_page_cache` to 222 MB. ⚠️ Its rows are `browsed = 1`, hence outside `POOL_WHERE`: no scoring impact, and they add nothing to the item sitemap. Watch `/api/health` → `facetSweep`. → `docs/seo.md`
- **A text search must never skip the providers because the local answer "looks good".** Any bar judges completeness from our OWN rows, and a title is a prefix of its own sequels: an exact match on "Blade Runner" hides *2049*, "Cars" hides *Cars 3*. Serve the catalog first and fast (`find()` takes `userId: string | null` for exactly this), keep the provider half, and make it cheap with a cache — `discover.search` was the last uncached provider boundary in the app. → `docs/archive/history.md` (catalog growth §14)
- **A list whose sort key half its items do not carry is not sorted — it is served in ARRIVAL order.** One feed skipped `decorateSection`, so every result carried `communityVotes ?? 0` and a stable sort showed ascending DATE order under a control labelled "Popularity". ⚠️ Its sibling: a dedupe keyed on title+type with NO YEAR drops the second work sharing a name, and oldest-first arrival makes that always the NEW one — so search reads as "we don't have it". → `docs/archive/history.md` (grep "could not find a new title")
- **The pageview beacon gates on a request SHAPE, not on a user-agent name.** A UA list only catches what somebody thought to name, and prod took 9,917 crawler views in a day past one. `isSameOriginBeacon` requires `Origin` or `Sec-Fetch-Site` to agree with the host, which no scripted client sends whatever UA it claims. ⚠️ Requiring only ONE marker is the precision half (pre-16.4 Safari sends no `Sec-Fetch-Site`), and it compares HOSTS, because Railway terminates TLS so the request reads `http:` while the browser sent `https:`. ⚠️ It cannot catch a real headless Chromium; `TELEMETRY_AGENT_SAMPLE` logs a 1-in-20 UA sample to name that one. → `telemetryBeaconShape.test.ts`
- **"Which surfaces does a display preference reach" is a PRODUCT question, and the honest default is every surface that CHOOSES on the viewer's behalf.** Scoping it by reading the implementation ("trending comes out of the viewer-independent snapshot") rather than the screen is how a hidden show stayed in "Popular right now". Filter in the PER-USER OVERLAY (`withUserOverlay`), which keeps the snapshot built-for-nobody and crawler-cheap. ⚠️ When the preference must also stay REACHABLE, gate on the search term, not on the surface: the Progress tab is served hidden rows flagged and drops them unless `f.q` is set, so "not in the feed" and "findable by name" are both true. → memory `old-site/hidden-items-and-destructive-testing.md`
- **A new user-scoped table has THREE obligations and only one of them is automatic.** Erasure is schema-derived and free (a literal `user_id` column). The export is written by hand (explicit column lists) and `dbPrune.ts`'s `PRUNABLE_WHERE` needs the table by name, or hiding/marking a `browsed = 1` row UNDOES ITSELF on the next deploy: the prune deletes the item, the cascade takes the preference, and the title walks back. Walked end to end for `user_hidden_items`. → `src/lib/hiddenItems.ts`

## UI, layout, and the browser pane

- **React's synthetic `onMouseEnter`/`onMouseLeave` follow the REACT tree, so a PORTAL breaks them permanently.** A portalled child (ActionCells' star picker) is a React descendant wherever it renders, so moving the pointer into it is not a "leave"; when it then unmounts under the cursor React tracks a detached node and that element never receives another leave event. The tooltip stayed pinned open forever. Track hover with NATIVE listeners on the element, which are computed from its own DOM box. ⚠️ Diagnose by attaching both kinds at once: native enter 1 / native leave 1 / tooltip still open is the whole proof. → `posterCardHoverListeners.test.ts`
- **A detail surface gets the value its parent DERIVED, never the raw prop it derived it from.** PosterCard resolves a `fandexPending` card's score client-side and handed the untouched `item` to the explainer, whose layout branches on `fandexScore != null`: the card read 78 while the tooltip showed a date and a type chip and never fetched the breakdown. Both objects satisfy the prop type and both render, so only a person looking at it catches it. `posterCardTooltipScore.test.ts` pins both surfaces. → memory `old-site/card-list-components.md`
- **When ONE component is fed by TWO routes, every field the shared code reads must arrive from BOTH.** The missing half fails silently, as an inert control rather than an error (`/library` and `/wishlist` are one component over two routes). ⚠️ **`addedAt` describes an EVENT, not the item**, so a merge cannot resolve it by keeping the richer copy. ⚠️ A check naming one of two surfaces sharing a component is testing its luck. ⚠️ **A `route ===` condition inside such a component is a bug waiting for whichever route the nav prefers** — branch on `activeTab`; `route` is for building URLs. Pinned by `components/myStuffRouteConditions.test.ts`. → memory `old-site/shared-view-two-routes.md`
- **A control the shared toolbar renders on a tab must be consulted by that tab.** SubBar puts search, type chips, sort and the Filters sheet above every list page, and MyStuffView returned early for Progress with no state passed at all — four visible controls that did nothing for twelve days. Wire them or don't render them; "they don't apply here" is indistinguishable from broken. ⚠️ **Every filter in this app is client-side, so a filtered list must be fetched WHOLE**: a filter over one page of a paged list finds only what you already scrolled past. → memory `old-site/shared-view-two-routes.md`
- **A Settings save that changes a per-user preference MUST call `resetSessionProbe()`.** `sessionProbe` caches `/api/auth/me` in a module-level promise that client navigation never remounts, so without it every list keeps the old value until a full reload, which is indistinguishable from a broken setting. ⚠️ One save function having it is no evidence about its neighbour; check each. ⚠️ **A per-user setting is a DEFAULT, not a scope**: never hide the control that undoes it, or you ship an un-emptyable list. → [[user-display-preferences]]
- **A facet id is computed SERVER-side, always.** The list routes ship `sources[].data` as `{}`, and `extractFacets` reads people, companies and franchises straight out of those blobs, so a client-side re-derivation sees TAGS ONLY — and a pill matching nothing looks exactly like a genuine zero. Every route that filters carries `facetIds`; `matchesFacetIds` is the only matcher, and `matchesFacets` is deleted so `tsc` rejects the old shape. ⚠️ A PARTIAL `facetIds` (non-tag only, to save bytes) is `data: {}` wearing a different name: all four kinds or none. → `src/lib/listRouteFacetIds.test.ts`, memory `old-site/shared-view-two-routes.md`
- **An `/api/` response is compressed ONLY because `lib/compressResponse.ts` does it; Next will not.** A NEW route gets gzip only if it goes through `withUser`/`withOptionalUser` or wraps its own return; otherwise it ships raw. **Price a payload in GZIPPED bytes** (`/api/library` 9.77 → 2.23 MB), so a field-trimming idea is worth about a quarter of its raw figure. → `docs/archive/history.md` (grep `gzip /api/`), memory `old-site/shared-view-two-routes.md`
- **Anything a CLIENT component renders must never reach a module that imports `db.ts`.** The failure is a 500 on the page with tsc, lint and every test green, because nothing but loading the page exercises the client/server module graph. The fix is a LEAF module with no imports, shared by both halves. ⚠️ `import type` is erased and always safe; a runtime value is not. ⚠️ Turbopack caches the bad graph, so delete `.next` before believing a stale `Module not found`. → memory `old-site/home-snapshot-and-crawlable-rails.md`
- **CSS visibility is not conditional rendering.** A `lg:hidden` tree plus a `hidden lg:block` tree puts BOTH in the DOM, so every client island in them mounts twice and images inside `display:none` still download. Switch the *layout* with CSS and render the CONTENT once. Static paired title/nav elements are fine and deliberate (it removes one from the a11y tree). → memory `old-site/item-detail-mockup-rebuild.md`
- **A section above the fold that renders `null` while loading is a layout shift, and a skeleton alone cannot fix an auth-gated one**. The client only learns someone is signed in when the same round-trip lands. Read the session in `page.tsx` for a `signedIn` boolean and pass it down; a crawler is anonymous and gets byte-identical HTML. ⚠️ A placeholder must match the real box, MEASURED. The first attempt was 36px short, plus 4px of scroller padding, and those deltas are additive. → memory `old-site/home-snapshot-and-crawlable-rails.md`
- **A page-level `min-h-screen` inside a padded wrapper guarantees the page scrolls**: 100vh plus the padding exceeds the viewport by construction. `<body>` already carries it. Derive bottom padding from `--size-nav-bar-mobile` plus `env(safe-area-inset-bottom)`, never a flat guess. **Measure `scrollHeight - innerHeight` and expect 0.** → memory `old-site/calendar-day-first-and-viewport-fit.md`
- **When a surface must not jank, the fix is a layout that cannot change size, not smoother transitions on one that does.** Measure the budget with a `ResizeObserver` on a `flex-1` element (its height comes from the VIEWPORT, so it cannot feed itself), give children explicit pixel heights that sum back, and let the arithmetic decide the design. Give BOTH states of a disclosure the same size, and put a status line in a slot that always exists. ⚠️ `overflow-hidden` on the page root makes it the sticky SCROLLPORT. → memory `old-site/calendar-day-first-and-viewport-fit.md`
- **A `position: fixed` overlay is trapped by ANY ancestor with a `transform`, `translate`, `rotate`, `scale`, `filter` or `container-type` — including a ZERO-valued one.** Tailwind v4's `translate-y-0` sets the standalone `translate` property. ⚠️ Walking ancestors for `transform` will NOT find it (`transform` reads `none` while `translate` reads `0px`). The fix is a PORTAL to `document.body`, never a `max-height`. Diagnose against a control: append your own `fixed inset-0` div and compare heights. → memory `old-site/fixed-overlay-containing-block.md`
- **Three ways hover breaks, and one way a working hover LOOKS broken.** Tailwind v4's preflight leaves `<button>` at `cursor: default` (fix it once in `@layer base`). A `hover:bg-*` utility cannot beat an inline `style={{ background }}`: put the values in custom properties and let utilities switch them. ⚠️ **A browser pane that isn't displayed stops compositing AND starves the whole rendering loop** — `getComputedStyle` returns the START value of every transition, CLS reports zero either way, `(hover: hover)` is FALSE, and `requestAnimationFrame` / `ResizeObserver` / `IntersectionObserver` never fire. Inject `* { transition: none !important }` before measuring, and **run a control** against the old code. ⚠️ A tab never fronted reports `innerWidth: 0`, so every geometry read is garbage; assert `innerWidth > 0` in the same probe. → memory `old-site/hover-and-cursor-traps.md`
- **"The nav reaches every page" is not the same claim for every session state.** `AppNav`'s "You" slot is a link for a signed-in visitor and a `SignInDialog` button for an anonymous one, and `/profile` additionally `router.replace("/")`s anon before its footer renders. Verify a reachability claim separately for every auth branch the nav renders differently for. → memory `old-site/anon-legal-reachability.md`
- **`truncate` does nothing without `min-w-0`.** Verify any mobile layout at 320/360/412. → memory `old-site/mobile-viewport-overflow.md`
- **`/library`, `/wishlist`, `/settings` and the FACET pages are dead under `next dev` only**. Use the `prod` launch config to verify them. ⚠️ `/settings` renders the SIGNED-IN chrome with every field empty rather than a spinner, which reads as data loss. → memory `old-site/unhydrated-page-diagnosis.md`

## Design tokens

- **A `@theme` custom property read ONLY through an inline `var()` is TREE-SHAKEN**. It resolves to `""`, the declaration is invalid, and the element inherits. No build, lint or test error. Declare such tokens in a plain `:root` block instead. Check with `getComputedStyle(document.documentElement).getPropertyValue('--your-token')` returning `""`. → memory `old-site/tailwind-theme-tree-shaking.md`
- **A token's `@theme` prefix must be the utility's OWN theme key, and a wrong prefix generates NO RULE AT ALL.** `duration-*` resolves from `--transition-duration-*`, so `--duration-base` left ~28 call sites at Tailwind's default for three weeks with everything green. **Read the utility's real theme key** (`grep -o '"duration",[^;]\{0,300\}' node_modules/tailwindcss/dist/lib.js`) and **verify a matching RULE exists, not that the token resolves**. ⚠️ A naive `document.styleSheets` walk gives a FALSE NEGATIVE (CSS nesting empties `.cssRules`); test `selectorText` first. ⚠️ The scanner reads MARKDOWN, so doc prose emits real rules: "the rule exists in prod" is not proof a component uses it. → memory `old-site/tailwind-theme-tree-shaking.md`

## Tooling and lint

- **The `react-hooks/*` rules are ERRORS and the repo is error-clean.** Remaining `set-state-in-effect` flags sit on genuinely idiomatic patterns (storage hydration, prop→state sync, fetch-on-mount, load guards, layout measurement) with justified disable comments. Don't remove one without checking why it's there.
- **A push that doesn't reach prod is a CI problem until proven otherwise**. Healthy push→live is 3–5 min. → memory `old-site/ci-red-blocks-railway-deploy.md`

## Measurement discipline

- **Price a feature in RAM, not disk**. Memory is 77% of the Railway bill and volume ~9%, so disk is ~75× cheaper. Catalog size is a resident-pool cost first. → memory `old-site/railway-cost-shape.md`
- **`data/rr.db` IS NOT PROD, and a catalog number quoted without naming its database is how you tell Nils something false.** They disagree on the things a sweep is about: 4,292 items vs 6,037, 6,041 distinct tags vs 11,222, 27 `tag_category_override` rows vs 233 — and the hand-made tag categories carry DIFFERENT IDS on each (`people-characters`/`objects-elements`/`modes` locally, `character`/`object`/`mode` on prod), so code that hard-codes one set silently creates a near-duplicate on the other. Read prod over `railway ssh` (`/app/data/rr.db`, base64 the probe script in; never run `env`, it prints the API keys). → [[taxonomy-admin-editing]], memory `old-site/railway-cli-and-tool-sandbox.md`
